# AGENTS.md — rules for implementers of K-GroundControl

You are implementing K-GroundControl, a GPL-3.0 ground control station for PX4 and ArduPilot, in C++23 / Qt 6.12 for Windows and Linux. The PM (Claude) writes specs in Korean; you implement from the brief you are given. The user reads only what the PM writes.

**Authority.** `specs/BASE.md` (Korean) is the foundation and the original. This file is its English translation for implementers: it carries the rules of BASE that shape code; the full tables and every numeric value stay in BASE, which you must read. If the two disagree, BASE wins — implement BASE and put the discrepancy in your report (§7). Feature behaviour comes from the feature spec named in your brief (`specs/features/*.md`). Never implement anything the brief and spec do not ask for. Do not edit this file, `specs/`, or anything under `.pm/` except the report file your brief names.

**Read in this order before writing code:** this file → `specs/BASE.md` → the feature spec in your brief → the `MODULE.md` of every module you will touch.

## 1. Structure — modular monolith (BASE §1–§3)

One executable. Inside, modules with hard boundaries that talk only through public interfaces.

| Kind | Where | May depend on |
|---|---|---|
| Platform modules (know nothing about features) | `src/platform/app` (0) < `comm` (1) < `vehicle` (2) < `ui` (2.5) | lower platform layers only |
| Feature modules (one feature = one module, logic + screen) | `src/features/<id>/` | all platform modules + `api/` of features **ranked below** (§1.2) |
| Composition | `src/main/` (`main.cpp`, `Composition.cpp`) | everything; no logic |

### 1.1 Module layout and boundaries
Every module is one CMake static library target named `kgc_<path with _>` (`kgc_app_log`, `kgc_comm_mavlink`, `kgc_ui`, features `kgc_<id>` such as `kgc_esc`; header-only modules are INTERFACE targets; composition `kgc_composition`, executable `KGroundControl`). Every module depends on `kgc_app_errors` (the `ModuleId` type). Only `api/` is PUBLIC; `internal/` and `ui/` are PRIVATE. Platform sub-areas (`comm/mavlink`, `comm/espflash`, `vehicle/firmware`, `vehicle/safety`, …) are each a target of their own with their own `api/`, `MODULE.md` and namespace.

```
src/features/esc/
  api/kgc/esc/      EscService.h EscStates.h Errors.h ModuleId.h Settings.h(generated)
  internal/         logic, Constants.h, Events.h, settings/esc.settings.json, paths/<transport>/
  ui/               EscPanel.qml, EscController.{h,cpp}, register.cpp
  CMakeLists.txt
  MODULE.md
```
Platform modules and features without a screen (`terrain`, `gcsposition`) have no `ui/`. A feature module with no logic in that version may have no `internal/` (only `api/`, `ui/`, `MODULE.md`).

Rules the compiler and `tools/check` enforce — never work around them:
- Include public headers as `<kgc/<module path>/X.h>` (`<kgc/comm/mavlink/Mavlink.h>`, `<kgc/vehicle/firmware/FirmwarePlugin.h>`, `<kgc/esc/EscService.h>`). Never `#include "../.."`. Never include another module's `internal/` or `ui/`. `api/` headers never include `internal/` (use pimpl or interface + factory).
- Inside a feature: `ui/` → `internal/` → `api/`, one direction.
- Namespaces follow the module path: `kgc::app`, `kgc::comm::mavlink`, `kgc::vehicle::firmware`, `kgc::esc`.
- Size limits (physical lines incl. blanks and comments): file 400, function 60, QML file 300. Split instead of exceeding. Third-party and generated code are exempt.
- `MODULE.md` in every module (template §1.4, ≤100 lines). Update it in the same commit whenever the module's `api/` or its dependencies change.
- Platform code never names a feature. One explicit exception: the `OperationKind` enum in `platform/app/job` lists feature-named operations as labels only.
- Names come from the glossary in BASE §13. If you need a word that is not there, **stop and put it in your report** (you cannot edit `specs/`).

### 1.3 Lifetimes (BASE §3.1)
- **Global** modules: `Composition` creates exactly one instance for the app's lifetime (`shell`, `notify`, `appSettings`, `link`, `fcFlash`, `esc`, `elrs`, `tracker`, `map`, `video`, `gcsposition`, the `MissionEditor` part of `mission`, the viewer part of `logs`, the panel part of `ai`, the global lookup part of `terrain`, the app-log part of `analyze`). Global feature bundles: `TrackerStates`, `GcsPositionStates`.
- **Per-vehicle** modules: `Composition` creates them when a `Vehicle` appears and parents them to the `Vehicle` (`fly`, `vehicleInfo`, `preflight`, `layout`, `sensors`, `radio`, `flightModes`, `power`, `failsafe`, `motors`, `tuning`, `params`, the `MissionService` part of `mission`, the download part of `logs`, the per-vehicle part of `ai`/`analyze`/`terrain`).
- **Mixed** modules keep two separately named services (`LogsViewer` global, `LogDownloadService::of(vehicle)` per vehicle).
- Other modules obtain a per-vehicle service with the static lookup in its `api/`: `XService::of(Vehicle*)` (it finds the service among the `Vehicle`'s children). Controllers rebind on `VehicleRegistry::activeChanged`.
- Vehicle removal: `vehicleRemoved` signal → `deleteLater`. Hold vehicles only through `QPointer` or the active-vehicle property.

## 2. Toolchain and build (BASE §2, §15)
- C++23 (`std::expected`). GCC 13+ / MSVC 2022 17.8+ (CMake passes `/std:c++latest`). CMake ≥ 3.28 + Ninja. Presets: `linux-debug`, `linux-release`, `windows-release`.
- Qt 6.12 LTS. Allowed Qt modules per layer: `app` Core·Network·Sql·Positioning·TextToSpeech / `comm` + SerialPort / `vehicle` nothing more / `platform/ui` + Quick·Qml·QuickControls·QuickEffects·Graphs·Svg / features + Location·Multimedia·Graphs·Quick3D as needed.
- Dependencies: Qt via aqtinstall (pinned patch version) in CI; everything else via CPM with pinned tag **and** hash — including resource packages (icons: Tabler Icons 3.49.0 npm tarball URL + SHA-256, files listed in `resources/icons/icons.txt` are copied into the build by `cmake/icons/Icons.cmake`). Never vendor files by hand. No vcpkg.
- MAVLink: `mavlink/c_library_v2`, dialect **ardupilotmega**. Include only through `<kgc/comm/mavlink/Mavlink.h>`; allowed in `comm`, `vehicle`, feature `internal/`; never in `app`, `platform/ui`, any `ui/`.
- QML modules: `Kgc.Ui` (platform/ui) and `Kgc.<Id>` per feature, built with `qt_add_qml_module(... STATIC)`. `src/main` links them with `Q_IMPORT_QML_PLUGIN`, and `Composition` calls each feature's `registerUi(uiRegistry, service)` **explicitly** (a per-vehicle module with no global part — `vehicleInfo`, `preflight` — has `registerUi(uiRegistry)`, also called once at start-up; its controller rebinds to the active vehicle; a mixed module passes its global service) — do not rely on static initialisers (the linker drops them).
- Version lives only in `project(KGroundControl VERSION x.y.z)`; the about window, logs and artifact names read it.
- CI workflows: `check.yml` (structure checks only, no Qt; `tests/` runs as ctest inside `linux.yml`/`windows.yml`), `linux.yml` (AppImage), `windows.yml` (zip), `tracker.yml` (ESP32 images). Artifacts carry `LICENSE`, `THIRD_PARTY_NOTICES.md` (generated from the CPM list + `cmake/notices/extra.json`), and the source URL.

| Log messages (`KGC_LOG` text), also as shown in the app log window | **English**, short phrases, first letter capital, no full stop: values after a colon, clauses separated by commas ("Link lost: COM7, reconnecting in 3s"); no Korean, never translated (check `log_english`) |
| Terminal output (boot errors, option help) | Korean, telegraphic noun-ending phrases ("지원하지 않는 로그 수준: %1"); no sentence endings (…다/…요) |
| Strings shown on screen, `errorText()`, notifications, toasts | Korean source text wrapped in `tr()` / `qsTr()`, polite conversational ("…했어요"); English lives in `i18n/kgc_en.ts`; `Translator` changes the language and `Composition` connects its `languageChanged` to `QQmlEngine::retranslate()`, so the language switches without restart (Translator does not know the QML engine) |
| Identifiers, enum values, event and error names, commit subjects, this file, your reports | English |

Boot-time terminal output (command-line option descriptions, boot errors) is shown as Korean source text because no translator is installed yet; mark it with `QT_TRANSLATE_NOOP("BootOptions", …)` for the string check. Its English entries in `.ts` are reserved for a later terminal translation and are not shown now.

String checks: a Korean literal in C++ must sit inside `tr(`, `QT_TR_NOOP(` or `QT_TRANSLATE_NOOP(` (never inside a `KGC_LOG_*(` call); in QML, `text:`/`title:`/`placeholderText:`/`ToolTip.text:` literals must be wrapped in `qsTr(`.

Comment rules:
- Write why, not what. Do not restate the code.
- Every public class and function (everything in `api/`) has a docstring: first line its role in one sentence, then `입력` / `출력` / `실패` in that order.
- An entry point the user follows (QML action → controller method → service operation) also has a `흐름` section after `실패`: numbered steps in execution order, one per line, naming the call and what it does in plain Korean. The controller's 흐름 names the service operation; the service's 흐름 lists platform calls. Keep it in step with the code in the same commit.
- Code that comes from a spec starts with its source tag: `// [0.0.1 T4] specs/features/0.0.1-shell.md`. Shared rules: `// [BASE 9.2] specs/BASE.md`.
- A stub to be filled is marked `// WORKER-FILL: <what>`; whoever fills it removes the marker.
- Never: commented-out code, a TODO without an owner, change history, sentences mixing Korean and English.
