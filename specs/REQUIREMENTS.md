- 상태: **승인됨 (2026-10-24, 사용자)** — 초안 5, 설계 검토 4회(마지막 pass). 이후 변경은 사실 고치기만 하고 알리며, 3절 결정을 바꾸는 것은 다시 승인. D18·5.4절(안테나 트래커)은 2026-10-24 추가 승인. D19·5.5절(기체 구성도 편집)은 2026-10-24 추가 승인
- 이 문서가 정하는 것: 무엇을 만들고, 무엇은 만들지 않으며, 어떤 조건을 지키는가. 어디에 무엇을 둘지(구조)는 `specs/BASE.md`가, 기능 하나의 동작은 `specs/features/`가 정한다.
- 바탕 조사: PM 보관 문서 `.pm/research/inventory-ko.md`(QGC 기능 304개를 묶음 48개로 정리, 스택·차별점 조사 요약)과 원본 보고 9건. 저장소에는 넣지 않는다.
- "(미확인, 10절)" 표시가 붙은 요구는 조사에서 확인하지 못한 사실에 기대고 있다. 스펙을 쓸 때 다시 확인한다.

## 1. 한 줄 정의

PX4와 ArduPilot 기체를 위한 지상국(GCS). QGroundControl이 하는 일을 다 하면서, **처음 세팅하는 사람이 덜 헤매게** 하고, **ESC와 ELRS 수신기까지 한 프로그램에서** 설정하고 펌웨어를 굽는다.

## 2. 쓰는 사람과 상황

| 사람 | 상황 |
|---|---|
| 기체를 처음 조립해 세팅하는 사람 | FC·ESC·수신기 펌웨어를 올리고, 파라미터를 맞추고, 센서·조종기를 보정한다. QGC·Mission Planner에서 가장 많이 막히는 구간 |
| 비행을 운용하는 사람 | 연결하고, 상태를 보고, 미션을 짜서 올리고, 비행 중 명령을 내리고, 로그를 내려받는다 |
| 개발자(사람·AI) | 코드를 부분만 읽고 고친다. 전체를 읽지 않아도 된다 |

## 4. 기능 요구 — QGC 수준 (R-Q)

묶음 번호(A1…E5)는 `inventory-ko.md`의 것. **R-Q 행 하나의 범위는 그 묶음에 속한 원본 ID 전부**(예: R-Q11 = E1~E5 = C-50~C-66 전부). 묶음에 들지 않은 원본 ID는 아래 "추가 ID" 칸으로 배정한다. 기능 스펙은 묶음 하나 또는 그 일부를 단위로 쓴다.

추가 ID 배정: R-Q1 ← C-5(블루투스), C-9(연결 보류), C-10(링크·채널 한도), C-11(링크 품질·RADIO_STATUS), C-26(GCS 간 제어 넘기기, 미확인 10절) · R-Q2 ← F-16(끊김 처리), F-17(비행 상태 판정) · R-Q3 ← F-58(tlog 재생 화면, A6과 한 묶음) · R-Q5 ← F-36(속도 변경), F-43(그리퍼), F-44(다중 기체 일괄 명령), F-45(가상 조이스틱) · R-Q6 ← F-57(지도 엔진; GeoMap 3D 부분은 7절 나중 순서) · R-Q11 ← C-49(분석 화면 틀), C-67(도움말·첫 실행 안내) · R-Q7 ← P-10, P-11, P-15~P-20(미션 속도·카메라 구간·Plan 기본값), P-80~P-82(현재 항목 추적, 재개, AP go-to) · C-13(모의 링크)은 개발·테스트 도구로 BASE.md에서 다룬다(7절).

### 5.4 안테나 트래커 (D18)

QGC에는 없는 기능. Mission Planner의 GCS 주도형 트래커(GPL-3)가 동작 참고(소스는 아직 안 읽음, 10절). ESP32 쪽 굽기는 ELRS의 ESP 시리얼 부트로더 경로(R-D19①)를 그대로 쓴다. 원칙 하나: **트래커 기능은 기체에 MAVLink를 하나도 보내지 않는다**(스트림 속도 요청 포함). 기체 쪽은 읽기만 한다.

| R-D24 | **GCS↔ESP32 프로토콜은 우리가 정의한다.** USB 시리얼 기본(WiFi TCP는 나중 순서, 7절). 프레임에 프로토콜 버전·길이·시퀀스 번호·CRC, 명령마다 ACK. **식별 응답**(매직값·프로토콜 버전·스케치 버전·칩 ID·변종)이 연결 첫 단계이고, 프로토콜 버전이 GCS와 같을 때만 추적을 켠다(다르면 굽기 권유). **양방향 생존 신호**: GCS가 주기적으로 보내고, ESP32는 설정 시간(NVS) 안에 못 받으면 "끊김" 동작(R-D30). **모드는 하나만 활성**(대기·자동·수동·보정; 수동·보정 중에는 자동 지시 무시). 명령: 각도 지시(절대 방위·고각, R-D25), 상태 요청, 수동 조작, 보정 시작·종료, 설정 쓰기(서보 범위·반전·중립·슬루·히스테리시스 각·편각·생존 시간 초과 — 스케치에 박힌 **절대 한계 안에서만** 받음), 수동 정렬 고정("여기가 기체 방향", 그 순간의 기체 진북 방위를 실음), 부트로더 진입. 응답: 현재 서보 각, 자력계 헤딩(보정 중에는 원시 값 스트림), GPS(fix·위치·MSL 고도), **서보 레일 전압**, 마지막 리셋 원인(브라운아웃 포함), 모드·오류 코드. 바이트 명세는 기능 스펙에서 | D18 |
| R-D25 | **각도 기준과 헤딩**: GCS는 **진북 기준 절대 방위**와 고각만 보낸다(서보 각은 보내지 않는다). 트래커의 헤딩은 GPS 모듈에 함께 있는 I2C 자력계가 맡는다. 모듈은 **팬 판 위, 틸트 축 아래**에 단다(팬과 함께 돌지만 틸트와 함께 기울지 않도록; 고각이 커져도 헤딩이 틀어지지 않게). **구동 방식**: ESP32는 서보가 정지한 동안에만 자력계를 읽어 **받침 정면 방위 = 자력계 헤딩(자북) + 편각 − 현재 팬 서보 각**을 갱신하고, 팬은 **서보 각 = 목표 방위 − 받침 정면 방위**로 구동한다(이동 중에는 자력계를 안 읽음). 범위 판정과 히스테리시스(R-D26)는 ESP32가 한다. 편각은 GCS가 설정값으로 써 준다(사용자 입력 또는 위치 기반 모델 — 미확인, 10절). **수동 정렬**은 보조 모드: 자력계가 없거나 자가 진단(값 범위·I2C 응답)에 실패하면 사용자가 수동 조작으로 팬을 기체 쪽으로 맞춘 뒤 "여기가 기체 방향" → GCS가 **수동 정렬 고정 명령에 그 순간의 기체 진북 방위를 실어** 보내고, ESP32는 **받침 정면 방위 = 그 방위 − 현재 팬 서보 각**으로 저장한다. 이후 명령 형식은 그대로 절대 방위다. 기체 거리가 설정값보다 가까우면 정렬 버튼을 막고, 트래커 위치가 바뀌거나 전원이 다시 들어오면 "정렬 다시 하기"를 표시한다. **자력계 보정**은 서보 출력을 멈추고 **기준 자세(팬 중립·틸트 0°)**에서 사용자가 트래커 전체를 손으로 한 바퀴 이상 돌리며 하고(팬 180°로는 한 바퀴를 못 돌므로), 결과는 ESP32 NVS에 저장해 상태 응답으로 돌려준다. 서보의 자석·전류가 만드는 간섭은 자세에 따라 달라 보정에 안 들어가므로, **헤딩은 서보가 정지한 동안 읽은 값만 쓰고**(이동 중 값은 버림), 팬·틸트 각에 따른 잔여 오차는 기능 스펙에서 실측해 보상표를 둘지 정한다(간섭 정도·받침 기울기 보정은 미확인, 10절) | D18 |
| R-D26 | **범위 밖 처리**: 팬은 정면 기준 −90°~+90°(서보 180°), 틸트는 수평 0°~천정 90°. 팬: 방위가 범위 밖이면 **마지막으로 닿은 한계에 머물고**, 반대쪽 한계로는 기체가 범위 안으로 돌아왔을 때만 옮긴다(히스테리시스 각은 설정값; 뒤를 지나는 기체 때문에 180° 휩쓸지 않도록). "추적 불가"를 표시하고 트래커를 돌려 재정렬하도록 안내한다. 틸트: 계산한 고각을 0~90°로 자르고(음수는 0), 추적 불가 중에도 계산값을 따른다 | D18 |
| R-D27 | **ESP32 스케치는 저장소 `tracker/`에 포함**(GPL-3; 위치·구조 검사 적용 여부는 BASE.md, 툴체인 버전 고정은 R-N18). 서보 PWM 2채널(LEDC; 부팅 중 흔들리지 않는 핀, 스트래핑 핀 회피 — 미확인 10절), 자력계(I2C; QMC5883L·HMC5883L·IST8310 중 모듈에 있는 것을 자동 식별), GPS(UART, NMEA/UBX), R-D24 프로토콜, 설정·보정값·마지막 각 저장(NVS). **부팅 뒤에는 NVS의 마지막 각(없으면 중립)에서만 PWM을 시작하고 첫 지시가 올 때까지 그 자리를 지킨다.** 중립 복귀·설정 변경·한계 이동을 포함한 **모든 위치 변화는 ESP32 쪽 슬루 제한**을 거친다. 지원 ESP32 변종과 핀 배치는 기능 스펙에서. 빌드는 CI가 같은 태그에서 해서 변종별 이미지(bootloader·partitions·boot_app0·app 또는 병합 이미지)와 주소표를 낸다(도구 PlatformIO/ESP-IDF 미확인, 10절). 스케치가 링크하는 코어·라이브러리 라이선스는 R-N22 고지·SBOM에 넣는다 | D18, R-N18, R-N22 |
| R-D28 | **굽기**: ESP 시리얼 부트로더 경로(R-D19①) 재사용, 포트 임대 R-Q1a (가)형. 스케치 이미지는 **같은 태그에서 CI가 빌드한 것을 설치본에 포함**(실행 중 내려받기 없음 — 비공개 Release는 협업자만 받을 수 있으므로). 대상 포트는 ① 기체 링크·ELRS 작업이 연 포트가 아니고 ② 굽기 직전 R-D24 식별 응답이 올 때만 허용한다. 식별이 안 되는 **빈 보드의 첫 굽기**는 사용자가 포트를 직접 고르고 칩 계열을 확인한 뒤 길게 눌러 확인해야만 한다(타깃명 재입력은 하지 않음). 굽은 뒤 MD5 검증과 재연결·식별 응답 확인. GCS는 **일반 연결 때 DTR/RTS를 리셋 쪽으로 움직이지 않는다**(ESP32 개발보드는 DTR/RTS로 리셋되므로, 굽기 때만) | R-D17, R-D19, R-D20, elrs F-3·R-8 |
| R-D29 | **화면**: 트래커 연결 상태·모드·헤딩·현재 각도·GPS fix·서보 레일 전압, 지도에 트래커 위치와 팬 범위 부채꼴, 추적 대상 기체 선택, 위치 출처 선택, 수동 조작 슬라이더(시험용), 자력계 보정 마법사, 수동 정렬 버튼, 설정(서보 범위·반전·중립·슬루·시간 초과·히스테리시스·편각 — 직접 입력 또는 위치로 계산) | D18 |
| R-D30 | **안전**: 트래커는 기체에 어떤 MAVLink도 보내지 않는다. 서보 급가속은 ESP32 쪽 슬루 제한으로 막는다. GCS 생존 신호가 끊기면 ESP32는 마지막 각도를 유지한다(설정으로 중립 복귀 선택, 그때도 슬루 적용). 서보 전원은 USB와 분리한 **외부 전원(공통 접지)**으로 하고, 브라운아웃 리셋이 상태 응답에 보이면 경고한다. 수동 조작·보정 화면에 "손 끼임 주의" 안내. **시동 중**: 트래커 **굽기는 거부**(R-N10; 포트 오인 시 조종 중인 ELRS TX를 덮어쓸 수 있음), 설정·보정·수동 조작은 허용하되 "추적 중단" 경고 | D18, R-N10 |

### 5.5 기체 구성도 편집 (D19)

초보가 막히는 지점은 "이 설정이 기체의 어디에 영향을 주나"를 모르는 것이다. 그래서 기체 그림 위에 부품을 놓고 그 그림을 보면서 설정한다. 모양은 Xpadder(게임패드 사진 위에 버튼 표식을 끌어 놓고 키를 배정하는 도구)와 같다. 어느 GCS에도 없는 기능(QGC는 PX4 Actuators 페이지에서 모터 위치 그림과 시험만, S-59). 이름은 R-N6의 2층 "기체 모델"(코드 계층)과 겹치지 않게 **"기체 구성도"**로 부른다. 1차 범위는 멀티콥터·비행기·VTOL; Rover·Sub·헬리콥터는 나중 순서(7절). 펌웨어별 대응표(R-D33)는 펌웨어 플러그인 계층(R-Q12)이 갖는다. 편집기는 **활성 기체 하나**에 묶인다.

- Windows: 사용자 PC에서 Actions 아티팩트 실행(비공개 저장소라 GitHub 로그인 필요; 보존 기간·러너 분 한도는 확인 필요)
- 실기: 사용자가 FC 하나 연결(개발 머신 계정을 `dialout` 그룹에 넣어야 함). ESC·ELRS 경로별 시험 장비는 그 기능 스펙 때 정한다
- GPS+나침반 모듈: **사용자 보유 u-blox GPS 모듈**(M8N 또는 M10 계열; 드론용 모듈은 보통 u-blox **UART** + 자력계 **I2C**(QMC5883L·HMC5883L·IST8310 중 하나)가 한 보드)을 기준 장치로 쓴다. 두 자리에서 시험한다 — ① **안테나 트래커 ESP32에 직접 연결**: UART로 위치(R-D23), I2C로 헤딩(R-D25). 모듈은 **팬 판 위, 틸트 축 아래**에 단다 ② USB-UART 어댑터로 PC에 연결해 GCS 위치 수신기로(R-Q3, R-D23 ②; 이때 자력계는 안 쓴다). NMEA 기본 출력과 UBX(NAV-PVT) 둘 다로 시험한다. 정확한 모델명과 자력계 칩은 기능 스펙 때 적는다
